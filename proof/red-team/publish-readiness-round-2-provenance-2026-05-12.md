## P0 findings (3)

### P0-1. Model identifier is generic, not exact: `Opus 4.7` is printed; the model actually used is `claude-opus-4-7[1m]` (1M-context variant)

The package uniformly advertises "Anthropic Claude Opus 4.7":

- `README.md:11` — "(Anthropic Claude Opus 4.7 driven by an operator orchestrator) under"
- `DEVELOPMENT.md:11` — "pipeline (Anthropic Claude Opus 4.7 + an operator orchestrator)"
- `DEVELOPMENT.md:253` — "by an LLM-agent pipeline (Anthropic Claude Opus 4.7 driven by an"
- `proof/proof.md:39` — "LLM-agent pipeline (Anthropic Claude Opus 4.7 + an operator"
- `Erdos625/README.md:9` — "generated by an LLM-agent pipeline (Anthropic Claude Opus 4.7 +"
- `paper/main.tex:41–42` — `\author{An LLM-agent pipeline (Anthropic Claude Opus~4.7 + an operator orchestrator)`
- `paper/main.tex:592` — "generated by an LLM-agent pipeline (Anthropic Claude Opus~4.7 driven"

`grep -rn "claude-opus-4-7\[1m\]" publish/erdos-625/` returns **0 hits**. The exact model used (verifiable from the Claude Code harness and from `operator-profile.yaml`-style configuration in the upstream `operator` project) is the **1M-context** variant — a materially distinct model: the 1M-context variant can hold the entire ~3.7 MB Lean tree (`PartBProfileBridge.lean` alone is 1.59 MB) in a single prompt, which the 200k-context variant cannot. This directly conditions what the pipeline can produce. An adversarial reproducer using "Opus 4.7" without `[1m]` will hit context-window failures on the very file (`PartBProfileBridge.lean`) where the legacy chain lives. The package documents the model imprecisely enough that a good-faith reproducer is set up to fail.

**Severity rationale (P0).** Mis-stating the model id of an LLM-generated mathematics submission is the canonical screenshot attack ("the package doesn't even name the model correctly"). PRISMA/CONSORT-AI-style and NeurIPS-reproducibility-checklist norms require model-version specificity; `[1m]` is part of the version string.

### P0-2. No statement of the same-model-audit blind-spot risk

Round 1 reframed "independent red-team passes" to "internal adversarial-audit passes (same LLM-agent pipeline)". The package says this *factually*:

- `README.md:13–14` — "The same LLM-agent pipeline also conducted the five internal adversarial-audit passes; these are **not** independent third-party reviews."
- `ROADMAP.md:32–33` — "The audits are internal, not third-party."
- `paper/main.tex:597–600` — "The five \texttt{/swarm-red-team} sessions referenced below were conducted by the same LLM-agent pipeline that produced the proof and are therefore \emph{internal adversarial audits}, not independent third-party reviews."

What the package **never says**: that this is a *methodologically dangerous* configuration, because the same model trained on the same data shares its own inductive biases and plausibility-driven failure modes; an internal audit by the same model is structurally incapable of detecting blind spots that are inherited from training. The published consensus in 2024–2026 LLM-for-math work (Sleeper Agents, ARC-Evals, METR scoping reports, Mathstral / DeepSeek-Prover-V2 disclosure templates) names this risk explicitly. The package discloses the *fact* (same pipeline) without the *consequence* (shared blind spots → critiques are not corrective on the model's systematic errors).

**Severity rationale (P0).** This is the round-2 mechanism claim's load-bearing gap. "Internal not third-party" is a procedural statement; the missing statement is the *substantive* one that makes the procedural one comprehensible to a reader who has not internalized recent LLM-evaluation literature. Without it, the disclosure functions as performative transparency — visible enough to satisfy the form, silent enough to evade the implication.

### P0-3. Who proposed the four paper axioms is not stated anywhere

The four paper-backed axioms (`lemma_7_20_modified`, `partB_alphaMinusTwo_firstMomentBelowOne_source`, `chi_alphaMinusTwo_lower_bound_whp`, `zeta_alphaMinusTwo_upper_bound_whp`) are the **entire** boundary between "published math + Lean-verified" and "this repository's contribution". The disclosure of *who proposed each axiom* — the human supervisor (axiom-as-strategic-decision) or the LLM-agent (axiom-as-proof-engineering-shortcut) — is the single most decision-relevant methodological fact for a proof depending on these four objects.

- `DEVELOPMENT.md:253–256` (ADR-10) — "The human supervisor selected the proof strategy at the branch-point level, accepted or rejected proposed proof steps, ran the Lean build, and chose which red-team findings to act on. The agents generated and edited the source."

This is the closest the package gets. "Selected the proof strategy at the branch-point level" is ambiguous: at the level of "use Heckel-2024 vs HP-2023"? at the level of "split on InMainRangeMod"? at the level of "axiomatize Lemma 7.20-modified rather than prove it"? An adversarial reader reads this and cannot tell whether the four axioms were the *human's* choices of citation boundary or the *LLM's* convenient termini.

Specifically: was the **hybrid** structure of axiom A1 (HP-2023 Lemma 7.20 weakened to require only $\mu_\alpha \ge n^{x_0+\varepsilon}$, closed by the in-repo numerical certificate) human-proposed (a mathematician's interpolation between two papers) or LLM-proposed (a plausibility-driven gap-closing shortcut)? Was the **extrapolation** structure of axiom A4 ($\alpha-1 \to \alpha-2$ symmetric move) human-proposed (a mathematician recognising a symmetry in HP-2023 §6) or LLM-proposed (an analogical leap that compiles)?

`grep -rn "proposed\|axiom proposal\|axiom origin\|human.proposed\|LLM.proposed" publish/erdos-625/` returns **0 hits**.

**Severity rationale (P0).** A reader scoring the contribution needs to know which side of the human/LLM line each load-bearing object sits on. Without this, the four-axiom inventory is procedurally honest but methodologically opaque.

## P1 findings (8)

### P1-1. The operator orchestrator is unnamed and unlinked

Every reference to the orchestrator is generic — "an operator orchestrator". `grep -rn "operator-profile\|operator-history\|github.com.*operator" publish/erdos-625/ --include="*.md" --include="*.tex"` returns **0 hits**.

- `README.md:11–14` — "(Anthropic Claude Opus 4.7 driven by an operator orchestrator)"
- `paper/main.tex:592–593` — "driven by an operator orchestrator"
- `DEVELOPMENT.md:253–254` — "(Anthropic Claude Opus 4.7 driven by an operator orchestrator)"

The framework has a name (`operator`) and lives in a separate repository at `/Users/thunderbird/Projects/operator/`; it has its own `AGENTS.md`, `policies/`, ADR history, and codex-acp / claude-code adapter layers. The publish package would not even tell the reader the framework's project name. Compare with the convention in human-collaboration papers, where each tool used (e.g. Mathlib, sympy, mpmath) is cited with name + version + URL.

**P1 because** reproducibility-of-process under any 2026 norm requires the agent harness to be nameable, version-able, and locatable. "An operator orchestrator" is not nameable.

### P1-2. No agent-side reproducibility artefacts are shipped

`find publish/erdos-625/ \( -name "*.yaml" -o -name "operator*" -o -name "AGENTS*" -o -name "*prompt*" \) -not -path "*.lake*"` returns only `.github/workflows/build.yml`. No `operator-profile.yaml`, no `AGENTS.md`, no `operator-history.jsonl` excerpt, no system-prompt snapshot, no skill-set listing for the Claude Code harness, no swarm-red-team configuration. `ROADMAP.md:140–154` ("Build prerequisites and reproducibility") names *only* the Lean toolchain, the Mathlib pin, the axiom snapshot, and the two `.py` numerical scripts. The LLM-process side of "reproducibility" is silent.

**P1 because** an outside reader running the same Claude model on the same Lean toolchain cannot re-derive the same proof without the agent harness configuration; the package presents reproducibility as a one-sided concept (Lean only) without naming the other side.

### P1-3. No reject-ratio order-of-magnitude statement; no statement of HIL granularity

`DEVELOPMENT.md:253–256` says the supervisor "accepted or rejected proposed proof steps". No statement of the *order of magnitude*: was the accept:reject ratio 1:1, 1:10, 1:1000? `grep -rin "rejected\|attempts\|iterations\|trials" publish/erdos-625/ --include="*.md" --include="*.tex"` returns generic uses only.

Equally unstated: was the HIL reviewing each Lean diff at the *tactic* level, each diff at the *lemma* level, or only at the *theorem statement* level? The three modes have wildly different correctness implications.

**P1 because** an adversarial reader will assume the worst (rubber-stamping) unless the package quantifies. A short qualitative statement ("typical lemma required 5–50 rejected attempts; each accepted diff was reviewed at the tactic level for the four paper-axiom files and at the lemma level for supporting modules") is the standard mitigation.

### P1-4. Cross-model capability of the operator framework is not addressed

The `operator` framework's adapter layer (per upstream `AGENTS.md:63–73`) supports a `codex_acp` adapter capable of driving non-Anthropic models — the canonical launch command lists `OPERATOR_CODEX_ACP__MODEL='gpt-5.4'`. This means the orchestrator *could have* used a different model for any subtask (e.g. a critique pass) and *could have* used cross-model auditing as a partial mitigation for the P0-2 shared-blind-spot risk.

`grep -rniE "GPT|Codex|OpenAI|cross.model|different.model|second.model" publish/erdos-625/` returns **0 hits**. The package therefore neither (a) claims cross-model auditing was used, nor (b) discloses that it was not. The adversarial reading is that this was the easy win the pipeline did not take.

**P1 because** it bears directly on P0-2; the disclosure could either claim cross-model mitigation (and would have to substantiate it) or explicitly acknowledge that cross-model auditing was available but not used.

### P1-5. `paper/main.tex:86–87` still has `\url{https://github.com/...(anonymized)}` after the round-1 honesty pass added named LLM-agent provenance

The author block names "Anthropic Claude Opus 4.7 + an operator orchestrator" (named), but the repository URL is anonymized:

- `paper/main.tex:86–87` — "The complete Lean development is available at \url{https://github.com/...} (anonymized)."

This is now internally inconsistent: the package presents itself as both "anonymized for peer review" (URL placeholder) and "published LLM-disclosure submission" (author block + 6 provenance callouts). For a GitHub-public release one of these has to give.

**P1 because** the inconsistency is a one-line read-and-fix; left in place it invites the reading "the authors copied an anonymized template, replaced the author line, and missed the URL line".
